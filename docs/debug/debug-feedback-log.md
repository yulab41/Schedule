# 调试反馈日志（Web 1.0 Debug / Test 阶段）

本文件是 Web 1.0 调试与测试阶段的用户反馈、修改意见、自查发现、修复与功能变更的持续记录。
每一轮修复对应一次 Git 提交；`docs/project-status.md` 保留当前状态交接，本文件保留完整轮次历史。

当前阶段：Web 1.0 线上调试与用户测试（功能已基本完整，按用户反馈持续修复/打磨），完善后进入微信小程序立项与实施（设计规格 26.1，另建独立实施计划）。

## 通用注意事项（调试期）

- PWA 缓存：Web 改动上线后提醒用户强制刷新；必要时升级 `apps/web/src/pwa/cache-logic.ts` 的 shell/schedule 缓存版本号。
- 部署：GitHub Actions 的 Deploy 由 Verify 成功触发；Verify 失败会导致该提交不部署（曾出现一次，见轮次 9）。判断是否上线以 `gh run list` 为准。
- 数据库：CynosDB 默认 `explicit_defaults_for_timestamp=OFF`，TIMESTAMP 列会隐式带 `ON UPDATE CURRENT_TIMESTAMP`，曾导致批量更新班次触发唯一键冲突（已修复并新增迁移 `0018`，见轮次 10）。后续涉及 TIMESTAMP 列定义时需显式写明默认值。
- 数据清理：2026-08-03 已按用户要求清空线上草稿与排班（23 个排班期间、638 条班次软删除，统计快照清空；模板/成员/岗位/班种/联系方式/事件历史保留）。
- 提交与推送：每轮完成验证后自动 commit 并 push `main`，CloudBase 部署由流水线自动执行。

### 轮次 10（提交 9531dd2）
- 用户反馈：删除草稿和覆盖草稿时提示“服务器暂时无法处理请求，请稍后重试”；要求清空现有草稿和排班。
- 我方自查发现：线上 CynosDB `explicit_defaults_for_timestamp=OFF` 使 `shift_assignments.starts_at` 隐式带 `ON UPDATE CURRENT_TIMESTAMP(3)`，任何批量更新都会把所有班次 starts_at 改成当前时间，触发 `(schedule_period_id, starts_at, slot_position)` 唯一键冲突 → 500。
- 修复/功能：线上 ALTER 修正列定义；新增迁移 `0018_fix_shift_assignment_timestamps.sql`；所有 `shift_assignments` 更新显式保留 starts_at（防再漂移）；按用户要求清空线上草稿与排班（23 期间/638 班次软删除、统计快照清空，模板/成员/岗位/班种/联系方式/事件历史保留）。
- 验证：线上删除序列实测通过；`pnpm verify` 336/336（含新迁移）。
- 状态：已完成。

### 轮次 11（提交 2834f07）
- 用户反馈/需求：
  - 草稿预览仍提示“服务返回了无效资料”。
  - 应用模板后不要按月拆成多份草稿，应是一条“开始到结束”的草稿；不要显示版本号。
  - 一次发布就是从开始到结束的整个排班，而不是每月点一次发布。
  - 手动排班处应有“发布记录历史”：按月份记录，新发布导致旧排班下线时旧版本自动归档；可查看、可删除、可追溯；显示当前月份排班是第几版。
- 我方自查发现：预览校验器只接受 `YYYY-MM`（后端已返回该格式，为部署时序/缓存造成的误报）；草稿无批次概念。
- 修复/功能：
  - 前端预览校验器兼容 `YYYY-MM` 与 `YYYY-MM-DD`。
  - 历史接口 `GET /schedule-periods/history`：返回全部非删除期间（含角色、月份、版本、时间、草稿应用范围与 operationId）。
  - 草稿按一次应用操作合并为一条：显示 `开始日期 至 结束日期 · 共 N 个月`，月份为可预览小圆片，不显示版本号。
  - 批量发布接口 `POST /schedules/publish-batch`：一次发布整个范围（单事务原子、幂等、支持覆盖/冲突确认）。
  - 排班发布记录：每月显示“当前已发布 第 N 版”+“已归档”旧版本；归档版本可查看/删除，当前发布不可删除。
- 验证：`pnpm verify` 337/337（含历史/批量发布/归档删除集成测试）。
- 状态：已完成，待用户测试验收。
