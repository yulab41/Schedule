每一轮修复对应一次 Git 提交；`docs/project-status.md` 保留当前状态交接，本文件保留完整轮次历史。

## 通用注意事项（调试期）

- PWA 缓存：Web 改动上线后提醒用户强制刷新；必要时升级 `apps/web/src/pwa/cache-logic.ts` 的 shell/schedule 缓存版本号。
- 部署：GitHub Actions 的 Verify 仍由 push/PR 触发；Deploy Development 自轮次 29 起仅手动触发。判断是否上线以 `gh run list` 为准。
- 数据库：CynosDB 默认 `explicit_defaults_for_timestamp=OFF`，TIMESTAMP 列会隐式带 `ON UPDATE CURRENT_TIMESTAMP`，曾导致批量更新班次触发唯一键冲突（已修复并新增迁移 `0018`，见轮次 10）。后续涉及 TIMESTAMP 列定义时需显式写明默认值。
- 数据清理：2026-08-03 已按用户要求清空线上草稿与排班（23 个排班期间、638 条班次软删除，统计快照清空；模板/成员/岗位/班种/联系方式/事件历史保留）。
- 提交与推送：每轮完成验证后按仓库规则 commit 并 push `main`；GitHub Actions 自动执行 Verify，CloudBase 仅在需要上线时手动触发 Deploy Development。

### 轮次 55（提交：feat(workflows): auto-archive stale completed workflows with monotonic ordering）
- 用户反馈/需求：实现“失效工作流自动归档/自愈”机制——检测 completed 但实际人员/资源已不匹配、且没有后续有效工作流的记录，自动写入撤销事件并归档（移出活跃数据区），不再阻塞后续操作或残留日历标签；完全自动化且幂等、可追溯；同毫秒创建的 createdAt 比较可能漏判，需要更可靠排序；用户确认可增加一次启动巡检扫描。
- 根因：completed 但实际失配的记录只在读模型标记 `isRevocable=false`，数据库状态不变；撤销入口要求实际人员匹配，因此这类记录既无法界面撤销、也无自动归档，日历标签（依赖撤销事件）和审批列表一直残留；`findLaterAssignmentWorkflows` 用毫秒级 `createdAt >` 比较，同毫秒可能漏判。
- 修复/功能：
  - 可靠排序：迁移 0026–0031 新增 `workflow_sequence_allocations` 共享单调序列，`swap_requests`/`duty_adjustments` 增加 `workflow_sequence` 并回填历史；换班/加扣班创建时在同一事务内领取序列；撤销顺序保护与自愈的“后续工作流”判断全部改按序列比较。
  - 自愈服务 `WorkflowSelfHealingService`：检测（completed + 实际人员不匹配 + 无后续有效工作流）与归档（写入 `swap_revoked`/`duty_adjustment_revoked`、状态置 `revoked`、版本 +1、不修改实际人员、刷新统计）；链式失效在一次归档中收敛，重复调用幂等。
  - 触发点集成：换班、加扣班各自 7 个事务入口（创建/直接操作/接受/审批/拒绝/取消/撤销）与排班补录（更新/新建既往班次）在同一事务内自愈。
  - 启动巡检：`createRuntimeApp` 创建时后台执行一次全库扫描（本地与 CloudBase 冷启动均覆盖），用 MySQL `GET_LOCK` 跨实例互斥，操作者记为空（系统），失败仅记日志。
  - 集成期自查发现的根因修复：触发点只传“本次操作涉及的班次”时，换班对端班次未被加载，被当作缺失误判为失配，导致链上有效记录被误归档；检测器改为加载工作流引用的全部班次后再判定。
- 验证：`pnpm verify` 通过（62 个测试文件 / 418 个测试），新增失效特征化、自动归档、链收敛与幂等、触发点端到端（换班取消/加扣班拒绝/补录改回）、启动巡检等测试；未部署 CloudBase。
- 外部状态：上线前需先对线上库执行迁移 0026–0031，再部署代码；部署后的启动巡检会自动清理线上既有失效残留。
- 状态：已完成，待部署验证。
