# 系统化调试执行章节

## 何时读取

存在可复现失败、根因未知、环境与代码归属不清，或同一根因症状重复出现时读取本章并加载
systematic-debugging。已知根因的普通实现、例行验证和发布清单不重复加载该技能。

## 最小闭环

1. 固定复现命令、SHA、工作树状态、工具链、输入和可观察输出；不把 sleep、timeout 或重试
   当成修复。
2. 对受影响的业务调用点执行 git log -S '<关键表达式>' -- <文件> 和 git blame，确认引入
   提交；只在需要历史证据时对 debug log 做精确 rg 和有界读取。
3. 先写旧实现会失败、新实现会通过的回归测试；实现最小修复，再跑同一组红/绿测试。
4. 对重构逐调用点审计 this/接收者绑定、异步拒绝与 catch 范围、空值语义、类型收窄、副作用
   和调用次数。任何差异都不是纯重构，应拆为行为变更。
5. 最后运行受影响包的 lint/typecheck/必要构建；核心 Web 链路按 web-api.md 补 browser smoke
   和 smoke:check-core。

## 证据与停止

- 证据必须标明静态检查、Node 自动化、用户人工操作、远端 health/verifier 或实体设备来源。
- guard 失败、staleWhen 命中或同一根因症状第三次出现时，停止增量补丁，重新检查前置条件和
  执行模型。
- 诊断输出不得包含 token、Cookie、Authorization、手机号、openid、session、完整请求/响应或
  生产数据；无法测量的指标明确记录为暂未验证。
