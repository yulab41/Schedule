# 微信小程序审计、优化与小米 14 体验版验收总规范

- 建立日期：2026-08-30
- 适用目录：`apps/miniprogram/**` 及与其构建、接口、测试、发布有关的共享代码和文档
- 主验收设备：小米 14（Android，微信客户端内的体验版）
- 文档性质：用户提供总规范的结构化完整转录；后续每轮必须结合 `docs/audit/STATUS.md` 只执行一个明确批次

## 0. 总目标与阶段边界

本项目需要一次完整、证据驱动、可回滚的微信小程序审计和优化。重点覆盖冗余与废弃代码、目录和组件职责、隐藏 Bug 与异步竞态、`setData`、页面加载和长列表、主包/分包/npm/静态资源体积、生命周期清理、重复请求和缓存、开发者工具与安卓真机差异、自定义导航栏/安全区/软键盘、Skyline 与 WebView 差异，以及不符合用户直觉的交互。

不得在一次会话中尝试完成全部工作。每轮以 `docs/audit/STATUS.md` 的唯一活动任务和停止条件为准。先测量，后修改；没有证据的问题不为“代码更漂亮”而重构。

## 1. 用户背景与沟通方式

用户是编程小白。所有问题、过程、操作指引和最终报告必须“通俗但专业”，顺序尽量为：

1. 用普通用户能听懂的一句话说明发生了什么、是否严重、是否需要处理。
2. 补充技术名称、根本原因，以及对性能、稳定性或体验的影响。
3. 给出明确操作：点击路径、需要截图或复制的内容、预期结果和下一步。

第一次出现专业术语时必须用一句话解释。不要只抛术语或原始命令，不假设用户理解 Git、构建产物、基础库、渲染引擎、主包或分包。需要用户操作时，一轮尽量不超过 3～5 步，每步写明点击路径、预期结果和需要反馈的内容。发生错误时先解释“这意味着什么”，再给解决办法；提炼日志重点，只保留必要原始错误；不要让用户猜截图页面或日志范围。最终报告必须先给普通用户版结论，再附专业技术明细。

表达示例：不要只写“可能存在 Skyline 与 WebView 的盒模型兼容性差异”；应先解释电脑模拟器和手机可能使用不同渲染方式，导致同一段样式偏移，再给出技术名词和明确取证路径。

## 2. 工具和资料使用规则

开始分析前先检查并读取当前环境中实际安装、实际可调用的能力：

1. 微信小程序开发 Skill，例如 `miniprogram-development`。
2. 微信开发者工具官方 Skill、`wechatide` 或开发者工具 MCP。
3. Skyline 相关 Skill。
4. Git 和 GitHub 工具。
5. 项目已有自动化测试、Minium、MiniTest 或截图测试。
6. 项目使用云开发时的 CloudBase Skill/MCP。
7. 仓库中的 `AGENTS.md`、`CLAUDE.md`、README、CONTRIBUTING、架构文档、测试文档和项目规范。

只使用实际成功加载且能调用的工具。禁止假装工具可用、编造工具名或参数、在失败后悄悄跳过、只凭模型记忆判断当前规则、只看普通博客而忽略官方 Skill/文档。仓库本地 `AGENTS.md` 若对工具执行有更严格限制，以更严格规则为准。

每轮报告必须列出：成功读取的 Skill、成功使用的 MCP/开发者工具能力、不可用工具及原因、因工具限制而无法验证的内容。

## 3. 主验收标准

唯一现有真实测试设备为小米 14，Android，运行于手机微信客户端；最终验收对象是上传后的微信小程序体验版。因此主验收事实是“小米 14 上通过微信客户端打开体验版后的真实显示效果、交互表现和运行结果”。

微信开发者工具模拟器仅用于编译、Console、Network、快速遍历、初步布局、自动化点击、模拟尺寸、生成预览二维码和上传前预检，不是最终视觉验收依据。不得仅凭模拟器宣称视觉验收通过、安卓显示正常、真机适配完成、体验版显示正常、跨端兼容通过或不存在真机兼容问题。

模拟器与小米 14 体验版不一致时，依次核对：

1. Git 提交和构建版本是否相同。
2. `develop` 与 `trial` 环境差异。
3. API、云环境、缓存和数据是否一致。
4. WebView 与 Skyline 是否一致。
5. 基础库、微信版本和字体设置。
6. 旧体验版或旧缓存是否已排除。

排除后以小米 14 体验版的实际表现为当前项目主验收事实。因没有其他实体设备，最终最多写“小米 14 体验版验证通过”或“当前安卓主测试设备验证通过”；不得写所有安卓兼容、iOS 已验证、全平台通过或所有机型完全一致。其他尺寸的模拟器检查只能补充风险，不能代替真机。

## 4. 修改和安全原则

1. 先测量，后修改；无证据不重构，不一开始重写整个项目。
2. 不擅自迁移到 Taro、uni-app、React、Vue 或其他框架。
3. 不改变现有业务逻辑、接口协议、数据结构、页面路由、已验收视觉设计和用户操作结果，除非原实现有明确 Bug。
4. 不以减少代码行数为目标，不为几行代码引入大型依赖。
5. 新增依赖前说明用途、是否进入主包、预计体积、轻量替代和能否不新增。
6. 不删除无法确认用途的代码；不直接修改构建生成文件，修改源文件后重新构建。
7. 不执行真实支付、正式发布、生产数据库破坏性写入、删除云资源、真实通知发送或其他不可逆操作。
8. 上传体验版前必须说明修改内容、版本描述、Git 短 SHA、是否含未提交修改、上传后测试页面，并取得用户明确同意。
9. 不破坏用户未提交修改：不用 `git reset`、强制 checkout，不擅自覆盖/删除、改写历史或遗忘恢复 stash。
10. 自动修复只限高置信、低风险、可验证、可回滚；大规模架构变化只写计划。

- TypeScript、ESLint、测试错误。

### 6.2 包体积

- 主包、每个分包和总包大小。

### 6.3 启动与首页

- 冷启动、首页首次渲染、首屏请求数。

## 7. “更多 → 测试工具”页面

在后续获准实施的阶段，优先在现有“更多”页面增加“测试工具”入口；不得在阶段 0 创建。若没有“更多”，选择不影响业务的调试入口并记录原因。页面优先进入独立测试分包，避免增加主包。

设计要求：普通用户看得懂，卡片分类，不直接展示大段 JSON；重要内容可一键复制；适合截图；顶部持续显示构建版本和环境；长内容提供“复制完整报告”；无横向溢出或过小字体；遵循项目现有视觉风格。

## 8. 测试工具必备模块

### A. 当前版本

显示当前环境（开发/体验/正式）、Git 短 SHA、构建时间、上传版本描述、小程序版本号、当前页面路径、是否以脏工作树构建、npm 构建产物时间、当前 API 环境和云环境。敏感数据必须脱敏。

### B. 手机与微信环境

显示手机品牌/型号、Android 版本、微信版本、基础库版本、renderer（WebView/Skyline/unknown）、Skyline 支持与版本（API 支持时）、屏幕/窗口宽高、`pixelRatio`、状态栏、安全区、字体设置、浅/深色、方向、网络类型。所有 API 先做能力检测；不支持时显示“当前微信版本不支持读取该信息”，不得崩溃。

### C. 页面显示检查

可勾选：顶部导航、胶囊遮挡、底部安全区、意外换行/截断、按钮错位、横向溢出、滚动、弹窗遮挡、fixed 漂移、图片拉伸、键盘遮挡、返回状态、切换卡顿、点击反馈、白屏/闪烁。提供“全部正常”“发现异常”“复制检查结果”。

### D. 关键测试场景

按实际业务列出首页、日历/排班、长列表、详情、新建、编辑、搜索、筛选、空/错误/loading、弹窗、底部面板、输入框/键盘、自定义导航/tabBar、图片、原生组件等入口。每项写点击路径、观察点、截图范围、正常结果和异常反馈方式。

### E. 性能信息

按当前基础库真实能力安全记录页面进入时间、首次数据显示、主要接口耗时与成败、数据量、缓存状态、最近页面切换和关键操作耗时、少量受控诊断日志。不得全局粗暴 monkey patch `setData`、长期保存大量日志、记录完整接口响应、显著拖慢业务或引入明显正式版开销。

### F. 网络诊断

如有统一请求层，在开发/体验版中记录最近若干次请求的接口名或脱敏 URL、开始时间、耗时、HTTP 状态、成败、缓存、重试、取消和重复。严禁记录 token、cookie、Authorization、手机号、身份证、openid、session_key、隐私数据、完整请求体/响应体或数据库敏感字段。

### G. 错误信息

安全、可控地显示最近若干页面错误、Promise 错误、网络错误、资源失败、关键业务异常、卸载后更新和重复提交警告。每项包含普通解释、页面、时间、技术摘要、是否影响继续使用。普通用户界面不展示数百行堆栈，完整技术内容只进入“复制完整报告”。

### H. 缓存和存储摘要

显示缓存项数量、占用、版本、旧结构、关键命中和解析失败。默认不提供“清空所有数据”。需要清测试缓存时，只清明确测试项，说明范围，二次确认，不删正式业务数据或登录态（除非用户明确同意）。

### I. 一键生成测试报告

“复制诊断报告”至少包含构建 SHA/时间、`envVersion`、页面、renderer、SDK/微信/手机/Android、屏幕窗口、安全区、字体、网络、API/云环境、近期性能、脱敏请求、错误摘要、用户勾选和问题说明。

另提供“复制给 Codex 的简化报告”，按普通用户可懂的栏目组织：当前版本、手机环境、当前渲染方式、发现的问题、相关数据和已截图页面。

## 9. 用户截图反馈流程

Codex 无法直接看到手机体验版时不得假装完成真机验证。每轮给出不超过 3～5 个清晰步骤，例如：打开体验版 → 更多 → 测试工具 → 截图版本/手机环境 → 复制简化报告并发回。

测试具体页面时必须写明打开路径、操作、等待时间、观察位置、整屏/局部截图或录屏要求、回到测试工具复制的指标。不得只说“请进行真机测试”。

用户提交截图后，依次核对构建 SHA、`trial`、renderer、基础库和微信版本，再分析视觉/性能。SHA 不一致时先明确“这张截图不是当前修改版本，暂时不能用来判断本轮修改效果”。

## 11. 静态代码审计范围

### A. 架构和目录

检查页面/组件/服务/工具/类型/常量职责，超大文件，页面直接操作底层 API，跨页重复业务逻辑，循环依赖，深层相对路径，超大 `index.ts`/barrel 及其整包副作用，公共模块反向依赖页面，不必要全局单例和隐式全局状态。

### B. 冗余和重复

检查未引用页面、组件、方法、样式、变量、静态资源，大段注释代码，重复工具函数/接口类型/请求封装/WXSS/图片图标，以及构建产物与源码重复引用。不得仅按文件名判断无用；必须结合全局搜索、`app.json`、分包、动态组件、路由和运行时调用确认。

### C. `setData` 和渲染

检查大对象或完整响应进入 `data`，改一个字段却传整个数组，高频 input/scroll/touchmove/定时器更新，非视图数据进入 `data`，隐藏/卸载后更新，无必要多次调用，observers 循环，以及 properties 传超大对象。

### D. WXML、WXSS 和布局

检查无意义嵌套和过深组件树、`wx:if`/`hidden`、不稳定 `wx:key` 或 index key、模板复杂表达式和重复过滤排序、不可见节点持续渲染、长列表分页/按需渲染、全局样式污染、动画布局抖动、固定高度截断、`flex-shrink`、rpx 舍入、自定义导航硬编码、安全区、软键盘、小米 14 适配及 Skyline/WebView 差异。

### E. 生命周期

检查未清理的 interval/timeout/监听，`onShow` 重复注册或全量请求，`onHide` 后昂贵任务，`detached`/`onUnload` 未清理，组件重建重复订阅，Promise 完成时页面已卸载，以及闭包长期持有大对象。

### F. 异步和隐藏 Bug

检查旧请求覆盖新请求、重复点击/提交、保存未禁用、Promise 未 await、异常未 catch、loading 异常不恢复、token 刷新风暴、缓存与网络互相覆盖、返回状态丢失、`null`/`undefined`/`0` 判断、时区跨天、快速切页错乱、乐观更新不回滚、授权拒绝、网络失败、弱网和超时。

### G. 网络和缓存

检查到处直接 `wx.request`、统一请求/错误/鉴权、重复并发、去重、取消、无上限重试、缓存过期、storage 过大、启动解析大数据、敏感数据明文、响应校验、大型校验库进主包、大数组重复排序映射过滤、反复 JSON 序列化。

### H. 包体积

检查主包最大模块、可迁分包页面、分包反向引用主包、多分包重复依赖、整库导入、日期/工具/图标/验证库、polyfill、Storybook/mock/fixture/开发日志进入生产包、超大或不合适图片、重复字体、大 JSON，以及测试工具是否进入主包或影响正式版。

### I. 交互体验

检查点击反馈、重复点击、loading 闪烁/全屏滥用、空/错/重试状态、表单错误定位、删除和返回误操作、滚动/筛选状态保留、键盘、弹窗安全区、触控区、禁用状态、弱网数据闪回、首屏白屏、不必要动画和普通用户直觉。

## 12. 问题分级和记录格式

- P0：崩溃、数据损坏、严重隐私/安全、生产不可用或真实业务损失风险。
- P1：首页/加载/包体/流畅度显著受损，高频竞态、重复请求、关键路径错误、卸载后更新、严重泄漏、小米 14 体验版明显异常。
- P2：中等性能、局部重复、维护成本或后续 Bug 风险、局部不合理交互。
- P3：低风险整洁、命名、注释或不影响当前功能的建议。

每个问题必须包含：编号、优先级、普通用户解释、技术解释、文件、位置、复现/证据、影响、根因、建议修复、风险、置信度、修复状态和验证方式。禁止只写“可能有性能问题”。

## 13. 自动修复边界

可自动修复高置信、低风险问题，包括已确认无引用的代码/资源、明确重复工具、未释放定时器/监听器、重复绑定/请求、卸载后 `setData`、未处理 Promise、loading 不恢复、错误 `wx:key`、无必要整对象 `setData`、开发/测试代码进生产、超大/重复图片、无效或整库导入、非首屏资源误入主包、重复提交、请求竞态、明确导航/安全区错误。

## 14. 体验版测试流程

### 阶段二：准备体验版

### 阶段三：小米 14 体验版验收

用户打开体验版，进入测试工具，截图版本和手机环境，执行关键路径，截图异常，复制简化报告并反馈。

### 阶段四：按真机证据修复

核对 SHA、`trial`、renderer、基础库，对比模拟器与体验版，判断来源，小范围修复，上传新体验版并只复验问题页面。
