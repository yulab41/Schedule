# Feedback25 访客日历与二维码性能证据

## 根因

- 月历 viewport 已按62px/行计算，但访客 month panel 未设置成员页已有的`rowHeight: 62`，共享组件回落到54px/行，五行月份产生约40px底部留白。引入对照为成员提交`83d8a03b`，Feedback24只同步了外层高度。
- 访客与成员列表使用同一ViewModel和WXSS；访客WXML遗漏成员提交`e94a54ca`已有的`dutyState`节点。结构归一化对比确认补齐后列表主体一致。
- 二维码慢不是排班数据量问题。旧服务仅有5分钟进程缓存；冷读取串行等待正式版微信码、审计事务、体验版微信码，客户端随后再并行合成两张卡片。刷新还需先完成visitorKey事务，再重复冷读取。

## 修改

- 仅访客month ring把三个panel写为62px rowHeight；仅访客列表补齐班种状态。成员日历文件零修改。
- schema61新增`group_visitor_qr_assets`，永久保存当前群组正式版/体验版原始二维码、MIME、长度与SHA-256；只有手动刷新visitorKey才在同一事务删除旧资源。
- 普通读取按内存→持久资源→微信生成顺序处理；首次缺失的正式/体验码并行生成，同进程重复请求合并。持久资源损坏或key不匹配时删除重建，迟到的旧key结果在锁定群组行后拒绝保存。
- 成功读取审计只记录生成数量、并行生成关键路径耗时和总耗时，不记录visitorKey、图片或群组资料。界面统一使用“刷新访客码”。
