# 小米 14 微信小程序体验版验收协议

- 设备：小米 14
- 系统：Android（实际版本由测试报告记录）
- 运行环境：手机微信客户端
- 验收对象：`trial` 体验版
- 证据目录：`runtime/audit/xiaomi14-trial/`（ignored，不提交 Git）

## 普通用户先看这里

简单来说：电脑里的检查只能证明“代码大致能构建”，不能证明手机上一定显示正常。本协议要求先确认
手机打开的是本轮同一个版本，再按少量明确步骤检查页面。只有这些真实结果通过，才能写“小米 14
体验版验收通过”。

## 1. 验收前置条件

开始一轮真机验收前，Codex 必须先给出：

- 本轮修改摘要和风险。
- Git 完整/短 SHA、工作树是否干净。
- 体验版版本号和含短 SHA 的版本描述。
- 需要测试的页面、操作、等待时间和证据。
- 明确说明未提交审核、未正式发布。

上传体验版必须先取得用户当次明确同意。本仓库禁止代理控制微信开发者工具 GUI/CLI；允许的上传只能
在当轮获得授权后使用仓库既有 Node `miniprogram-ci` 流程，或由用户人工完成。阶段 0 不上传。

## 2. 首先核对版本

收到任何截图或报告后，先核对：

1. `envVersion` 为 `trial`。
2. Git 短 SHA 与当前待验收提交一致。
3. 构建时间和体验版版本描述属于本轮。
4. renderer 实际值；本项目目标为 Skyline、无 WebView fallback。
5. 基础库版本、微信版本、Android 版本和手机型号。

任一版本信息不一致时停止分析，并告诉用户：“这张截图不是当前修改版本，暂时不能用来判断本轮修改效果。”

## 3. 第一轮通用操作（用户不超过 5 步）

测试工具页尚未建立时，按当轮给出的业务路径和版本说明测试；建立后使用以下固定流程：

1. 在小米 14 的微信里打开指定体验版，等待首页完全出现。
2. 点击“更多 → 测试工具”。
3. 截整屏“当前版本”和“手机与微信环境”。
4. 点击“复制给 Codex 的简化报告”。
5. 把截图和复制内容发回当前对话。

每个专项测试另给 3～5 步，必须说明打开路径、操作次数、等待时间、观察位置、整屏/局部截图或录屏，
以及需要复制的性能/错误/网络摘要。不得只说“请进行真机测试”。

## 4. 通用视觉和交互清单

- 顶部导航和胶囊不遮挡。
- 底部安全区正常。
- 文字不意外换行、截断或溢出。
- 按钮、弹窗、fixed 元素和图片不偏移或拉伸。
- 页面没有横向溢出，可以正常纵向滚动。
- 输入框不被软键盘遮挡。
- 返回后筛选、选择、滚动和表单状态符合预期。
- 页面切换、点击反馈、loading 无明显卡顿、白屏或闪烁。
- 关键按钮不能重复提交，失败后可以继续操作或重试。

## 5. 本项目关键路径模板

每轮只选与修改有关的最小集合，并补充准确页面路径：

| 场景           | 操作                          | 重点观察                            | 推荐证据            |
| -------------- | ----------------------------- | ----------------------------------- | ------------------- |
| 启动/工作台    | 冷启动并依次点击底部入口      | 首屏、白屏、入口状态、顶部/底部稳定 | 首页整屏 + 必要录屏 |
| 月/周/列表日历 | 切换月份和视图，打开详情      | 卡片重叠、闪烁、日期、状态保留      | 正常与异常整屏      |
| 通讯录         | 科室/人员模式切换、搜索、筛选 | 内部左右滑动、列表滚动、返回状态    | 切换录屏或两张截图  |
| 排班矩阵       | 横纵移动、选择、撤销          | 冻结层、跟手、掉帧、误触            | 录屏 + 性能摘要     |
| 新建/编辑表单  | 输入、打开键盘、保存、返回    | 键盘遮挡、重复提交、错误提示        | 键盘状态整屏        |
| 工作流         | 请假/换班/加扣班关键操作      | loading、竞态、冲突和结果           | 操作前后截图        |
| 弹窗/Sheet     | 打开、滚动、确认、取消        | 安全区、遮挡、背景滚动和关闭        | 弹窗整屏            |
| 弱网/失败      | 按当轮安全方案制造可恢复失败  | 错误解释、重试、数据闪回            | 错误页 + 简化报告   |

禁止执行真实支付、正式发布、破坏性生产写入、删除云资源或真实通知。业务写操作只有在当轮明确批准、
准备了安全测试数据和回滚方式时才可纳入。

## 6. 模拟器与真机不一致时

不要笼统写“电脑和手机不一样”。依次判断：构建版本、`develop`/`trial`、API/云数据、renderer、
基础库/微信、Android 字体、小米 14 屏幕与 rpx 舍入、系统字号、状态栏/安全区、原生组件、缓存、
异步竞态、图片和真实编译错误。排除旧版本和缓存后，当前结论以小米 14 体验版为准。

## 7. 证据命名和记录

文件名：`页面-状态-xiaomi14-renderer-buildsha.png`，例如
`schedule-month-normal-xiaomi14-skyline-a1b2c3d.png`。录屏使用相同前缀和 `.mp4`。

每条证据记录页面、状态、采集时间、短 SHA、`trial`、renderer、基础库/微信版本、操作步骤、预期、
实际和问题编号。用户只需在聊天发送证据，Codex 负责整理，不要求用户手工搬文件。

## 8. 验收结论口径

- 静态构建/测试通过：只能写“自动化基线通过”。
- 用户人工开发者工具检查通过：只能写“开发者工具人工预检通过”。
- 小米 14 体验版证据通过：可写“小米 14 体验版验收通过”或“当前安卓主测试设备验证通过”。
- 没有 iPhone/其他 Android：必须写“暂未验证”，不得写 iOS、所有安卓、全平台或跨端兼容通过。
