## 冷态与热态口径

- 热态：交错并轮换 15 个场景，先 warm-up，再连续 30 轮；不让某一种查询固定先预热其他查询。
- 冷态：每个场景、每轮都停止专用 MySQL；由于 dump/load 已关闭，InnoDB buffer pool 被清空；随后只对
  专用 Docker volume 文件执行 `POSIX_FADV_DONTNEED`，再启动 MySQL。每场景 3 个独立循环。
- 仅重启 API 从未被称为数据库冷态。MySQL 健康检查只执行 `SELECT 1`，不预热通讯录。
- 每次记录主查询和 count 的 P50/P95/max、actual rows/loops、examined rows、排序/临时表、逻辑/物理读、
  文件等待、锁时间、返回数量和分页状态。所有查询均未生成磁盘临时表，也未出现 buffer-pool wait-free。

## 原 SQL 诊断

首字母、中文姓名和完整拼音进入相同的文本 CASE 分支与相同根计划：先限定发布 batch/权限，再为候选
entry 逐条执行 employee-code、alias exact/prefix/contains 和 fulltext 条件。差异来自 alias 命中数量与
分支选择性，而不是独立的“首字母 SQL”。首字母主查询和 count 分别 examined 36,597/36,592 行；完整拼音
为 80,014/80,007 行。`INSTR` contains 分支按当前 batch 的约 1,200 个 entry 回查平均约 19 个 alias。

`mainQueryMs` 的 rows 段包含 Drizzle SQL 构造、已取得事务连接上的 driver 往返、数据库执行、结果读取与
driver 解码；不包含 permission、发布批次、contact 或 count，它们各有独立计时。MySQL 不存在 PostgreSQL
的 generic/custom plan 二选一；本实验使用 mysql2 prepared statement，每次由 MySQL 8.4 优化器执行。

## 四种方案的首字母结果

单位为 ms；冷态只列主查询 P50/max。覆盖索引为
`(entry_id, type, normalized_value)`，顺序来自实际计划中的 entry equality join、type 和 value 谓词。

| 方案            | 热 P50 | 热 P95 | 热 max |        冷 P50/max | 主/count examined | 冷物理读 P50 |
| --------------- | -----: | -----: | -----: | ----------------: | ----------------: | -----------: |
| 原 SQL          |   97.2 |  123.2 |  128.1 |     943.5 / 950.3 |   36,597 / 36,592 |        3,992 |
| 仅查询改写      |   70.4 |   82.1 |  170.3 | 1,018.5 / 1,023.3 |     1,205 / 1,204 |        3,992 |
| 仅覆盖索引      |   48.0 |   59.5 |   99.4 |     291.0 / 295.0 |   36,597 / 36,592 |        1,198 |
| 改写 + 覆盖索引 |   25.6 |   28.1 |   28.6 |     291.9 / 297.8 |     1,205 / 1,204 |        1,210 |

结论：查询改写解决扫描放大，但未减少冷页读取；覆盖索引解决大范围主记录回表和冷页读取，但不减少
examined rows。组合才同时满足两类目标。覆盖索引在合成 128,659 条 alias 上占 14,254,080B，三次创建
约 1.88–2.19s；会增加导入/发布写放大和磁盘占用。

## 语义门禁

同一快照逐条比较 13 类场景、49 个页面，差异为 0，覆盖：entry ID 集合与顺序、rank、精确总数、
hasNext、下一页 cursor、连续分页完整结果、空结果、member/owner/administrator/无权限和七级筛选。
精确 alias 没有短路其他模糊命中；各分支仍取同一 entry 的最高 rank；排序 tie-breaker、权限、分页和 API
返回结构不变。索引创建后再次执行相同门禁，仍为 0 差异。

## Buffer pool 独立候选

在无候选索引、原 SQL 下，每轮真实冷重启后轮换扫描全部通讯录主/二级索引，再运行首字母查询；每档 5 轮：

| buffer pool | 主查询 P50/P95/max | 物理读 P50/P95 | 总耗时 P50/P95 |
| ----------- | -----------------: | -------------: | -------------: |
| 128MiB      |  113.7/139.3/139.3 |          79/81 |    279.6/312.1 |
| 512MiB      |  115.6/120.7/120.7 |          77/81 |    279.9/293.9 |

本合成压力未显示可重复的中位收益，因此不建议单独调整 buffer pool。production 的相关工作集贴近 128MiB，
其他业务页仍可能造成逐出，但需先核对主机可用内存与长期 buffer 命中数据；不能用扩容掩盖扫描放大。

## 小程序请求收敛

- 中文输入保留静默 500ms 自动搜索和单汉字；ASCII、数字及 ASCII/数字混合只由现有键盘
  `confirm-type="search"` / `bindconfirm` 发起。
- 输入变化、清空、模式切换和筛选切换会清除未到期 timer；确认复用相同 in-flight/completed 查询。
- 回归测试先在旧实现上观测到完整拼音停在 6 字符、首字母、工号分别产生 6/3/4 条中间请求；修复后均为 0。
- 已有旧响应隔离、相同进行中 Promise 复用、失败/中止锁释放测试继续通过。未为 `abort()` 重构统一 transport；
  已发到服务端的 SQL 仍不能假设可被客户端取消。
- 页面已有键盘“搜索”确认入口，但没有额外的可见页面按钮；本轮按最小修复边界不做 UI 改版。

## 建议、生产影响与回滚

建议的最小正式服务端方案是：无筛选文本查询使用候选集合改写，带七级筛选继续使用原 SQL，并新增一个
`(entry_id, type, normalized_value)` 覆盖索引。它需要数据库迁移和按仓库规则执行的部署前备份；不需要 API
contract、客户端结构、停机或缓存变化。是否采用需由用户确认，本实验分支默认仍为 `legacy`，未启用候选。

回滚方式：应用先切回 legacy；随后删除新增索引。小程序请求收敛是独立提交，可单独回滚。正式执行前仍需在
生产等价预发布流程验证在线 DDL 时长、磁盘余量、导入发布耗时及回滚顺序。本轮没有修改 production、创建
production 备份、部署、上传体验版或更新主线。
