# 网页校对一次性重设基线

用户选择：以当前日历实际生效人员重设一次，以后继续识别本系统和网页的新变化。

- 原实现 `06d420a1` 每次读取 `plannedMemberName`，因而改校对快照会在下一次扫描时丢失；把基线永久改成实际值又会丢失本系统变化来源。
- 增加独立、不可随扫描更新的基线表；迁移 0072 仅一次捕获迁移时北京时间今天起、现有正式发布的头颈外科医生一线/全天班实际人员（实际字段为空时回退原计划人员），连同班次、期间、版本与捕获时间。原排班、工作流、事件及操作历史均保留。
- 扫描、写入前重读和撤回统一使用该班次的保存基线。日历实际人员仍按原始 actual ?? planned 读取，不能用新基线填补实际值。
- 以班次和期间绑定快照；以后换班不更新快照。新发布产生新班次，使用新版本原始发布人员为基线。日期已过、草稿、替换版、已删除数据不捕获；首次没有唯一匹配的日期仍由现有阻塞规则处理。
- 撤回再发布可能复用班次和期间编号，因此查询同时检查捕获之后的 `schedule_period_withdrawn` 事件。存在该事件即回退原发布基线；普通合并发布未替换的日期继续沿用快照，不按期间更新时间误判失效。使用既有期间/发生时间索引，历史快照和事件均保留。
- 旧检测记录必须重新扫描；旧确认请求的基线重读检查将拒绝已失效预览，操作历史保存操作时旧基线，撤回指向当前有效基线。
- 验证覆盖重设、后续变化、多次扫描、空值回退、重新发布、同步预览和撤回，以及真实 MySQL 迁移重跑不覆盖。
- 仅修改 API/数据库与必要发布校验，Mini 契约/页面不变，无新增依赖。生产迁移时点才是线上重设时点；部署前停写并备份，迁移后先检测再人工确认任何同步。未获本轮明确生产授权前仅交付已验证的代码检查点。
