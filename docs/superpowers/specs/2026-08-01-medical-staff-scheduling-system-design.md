# 多用户医护排班系统项目框架与设计规格

- 文档日期：2026-08-01
- 当前状态：设计已完成，等待最终书面审阅
- 第一阶段产品：医生排班 Web 1.0
- 正式部署目标：阿里云 ECS（Docker Compose：Nginx + Fastify + MySQL），中国大陆 IPv4 网络通过备案域名访问（2026-08-07 用户决定弃用 CloudBase）
- 预计首年规模：10–100 个群组、200–2000 名用户

## 1. 项目目标

建设一个供多个科室、多个排班群体共同使用的医护排班系统。第一阶段完成医生排班，重点解决固定顺序轮值、手动排班、请假重排、换班、加扣班、变更追踪、统计和提醒。后续在同一账号、群组和后端体系上增加微信小程序，再单独设计护士复杂排班。

产品必须满足以下原则：

1. 登录后立即看到当前月份每天的值班人员，不需要二次点击或跳转。
2. 自动排班结果可解释、可预览、可追踪、可撤销，不允许静默覆盖已发布数据。
3. 多用户同时操作时以服务器最新数据为准，任何旧数据都不能覆盖新数据。
4. 排班当前状态与不可修改的事件历史同时保存。
5. 每个群组的数据、规则、人员和权限相互隔离。
6. Web 优先，但后端和账号体系必须能直接服务后续微信小程序。
7. 第一阶段不保存患者、诊疗、考勤工资或其他医疗业务数据。

## 2. 第一阶段范围

医生排班 Web 1.0 包含：

- 用户名密码注册与登录、真实姓名、长号和短号。
- 保持登录状态，避免频繁重新登录。
- 群组创建、唯一四位群组码、自定义或随机群组码。
- 一名群主、多个管理员、群主转让。
- 管理员预建人员，成员通过定向邀请认领；不只凭真实姓名或群组码接管身份。
- 多个独立排班角色，例如一线、二线、三线和备班。
- 默认班种与群组自定义班种、时间、颜色和统计属性。
- 固定顺序自动排班和可重复使用的手动周期排班。
- 草稿、发布、自动生效、人工调整和排班版本。
- 全天业务日期请假、两种自动重排策略。
- 换班、自动接受设置、管理员审批设置。
- 加班、扣班及可相互抵消的加扣班统计。
- 排班事件中心和统计影响分析。
- 当前月份日历、法定节假日、调休工作日和快速拨号。
- 月度和年度值班统计。
- 站内通知和浏览器通知。
- 并发控制、审计、备份、监控、费用告警和正式部署。

第一阶段明确不包含：

- 患者资料和诊疗数据。
- 考勤、工资、绩效或费用结算。
- HIS、EMR 或医院统一身份系统对接。
- 短信提醒。
- 护士智能优化排班。
- 微信小程序客户端；但保留统一接口和账号关联能力。

## 3. 技术路线

### 3.1 总体选择

采用阿里云 ECS 自托管方案（2026-08-07 用户决定弃用 CloudBase）。开发阶段在 Win11 本地运行，正式上线后在 ECS 上以 Docker Compose 部署 Nginx、Fastify 与 MySQL，并接入备案域名。

### 3.2 开发语言与框架

- Web：Vue 3、TypeScript、Vite。
- UI：TDesign Vue Next，配合自定义日历和排班组件。
- 后端：Node.js、TypeScript。
- 数据库：MySQL；本地与正式环境均使用 Docker/ECS MySQL。
- 云端计算：ECS 容器运行 Fastify；定时任务由 cron/外部调度补充（暂未配置）。
- 测试：单元测试、MySQL 集成测试、接口测试和浏览器端到端测试。
- 包管理及项目组织：pnpm 工作区形式的单一代码仓库。

正式开发时使用当时仍受支持的长期支持版 Node.js，并锁定依赖版本；本设计不绑定尚未安装验证的具体小版本号。

### 3.3 代码边界

项目采用模块化单体，保持以下清晰边界：

- `web`：网页、PWA、日历和管理页面。
- `api`：HTTP 接口、认证上下文、权限和事务入口。
- `auth`：外部稳定 UID（字段沿用 `cloudbaseUid`）与本地业务用户映射；自建登录认证为后续任务。
- `groups`：群组、成员、群组码和权限。
- `scheduling`：自动排班、手动排班、发布和版本。
- `workflow`：请假、换班、加扣班和审批。
- `events`：排班事件和安全审计。
- `statistics`：月度、年度和变更影响统计。
- `notifications`：站内、浏览器及未来微信通知。
- `holidays`：国家节假日和调休数据。
- `shared-contracts`：Web、小程序和 API 共用的数据定义。

自动排班引擎写成不依赖页面和腾讯云的纯业务模块，以便单独测试和未来迁移。

### 3.4 本地环境

前置环境：

- Windows 11。
- Docker Desktop 与 Docker Compose。
- Git。
- Node.js 长期支持版。
- pnpm。
- 阿里云账号和独立 ECS 环境。

本地 Docker Compose 管理 MySQL、后端及反向代理。Web 可在容器内运行，也可为热更新直接运行在本机。业务数据使用本地模拟人员；身份认证集成测试使用本地认证端口。开发、测试和正式环境的密钥完全分离。

## 4. 账号、人员和联系方式

### 4.1 注册与登录

- Web 只向既有账号提供登录，不提供自注册、邮箱、短信或验证码页面。
- 授权管理员创建登录账号（自建认证为后续任务）；账号使用小写规范形式，Web 提交前去除首尾空白并转为小写，因此登录账号不区分字母大小写。
- 首次登录后，尚未建立业务资料的账号填写真实姓名；真实姓名用于展示和邀请目标核对，但不能单独用于接管群组身份，也不作为全局唯一用户标识。
- Web 密码输入仅要求非空，不限制长度、字符类型或复杂度；自建认证落地前为本地开发认证（无密码后端），业务数据库不保存明文密码。
- Web 登录状态由本地认证客户端管理；显式退出前可持续保持登录。
- 后续微信登录与现有账号绑定后继续使用原 UID 和排班数据。

### 4.2 联系方式

每个群组成员具有：

- 长号。
- 短号。
- 联系方式确认状态和最后更新时间。

短号按群组保存，因为不同医院或科室的短号可能不同。管理员可预填号码，成员认领后确认或修改。号码只对同群组有效成员可见，不向未加入用户或其他群组公开。电话号码不作为登录账号，默认不包含在统计导出中。

### 4.3 多群组

一个账号可以加入多个群组。真实姓名、权限、排班角色、长短号、自动接受换班设置和提醒设置均可按群组独立管理。

## 5. 群组、认领和权限

### 5.1 群组码与加入边界

- 每个活动群组拥有唯一四位数字群组码，支持随机生成和管理员自定义。
- 数据库唯一约束保证同一时刻不同群组不能使用相同群组码。
- 群主可以重新生成群组码，旧码立即失效。
- 频繁尝试群组码触发限频和验证码。
- 群组码只用于群组创建、管理和审计，不再提供注册用户按码加入；`/groups/claim` 与 membership-claim 端点保持删除。
- 删除群组进入 30 天回收期，群组码在回收期内不重新分配。

### 5.2 人员预建与邀请认领

1. 管理员预先录入或批量粘贴人员名单。
2. 群组内待认领人员的真实姓名必须唯一。
3. 管理员为目标人员创建邀请；注册用户通过邀请解析/接受进入认领流程。
4. 邀请按目标 membership/roster entry 绑定，不只凭真实姓名接管账号。
5. 匹配成功后加入并绑定该人员；邀请接受若合并账号，先保存 replacement token，再清 pending invite 并刷新上下文。
6. 没有有效邀请时，不开放成员数据；需要只读查看的用户只能按 catalog 走 `/join-guest`。
7. `left-member` 只能通过管理员邀请重新加入，不提供 claim 或再次 join-guest；历史重名由管理员处理。

### 5.3 权限角色

- 群主：每群组一人；负责转让群组、任免管理员、修改群组码和全部群组设置。
- 管理员：可有多人；负责成员、排班角色、班种、排班、审批和统计。
- 普通成员：查看已发布排班，提交请假、换班、加扣班申请，设置个人选项并查看统计。

平台管理员与群组管理员分离。平台管理员只负责服务运行、账号封禁、节假日数据和系统配置，不参与群组日常排班；其所有管理行为同样接受审计。

### 5.4 排班角色

排班角色与权限角色严格区分。群组可以创建一线、二线、三线、备班等多个排班角色。每个排班角色独立保存成员、固定顺序、班种、周期和重排规则。同一成员可以拥有多个排班角色，管理员本人也可以参与排班。

## 6. 班种

新群组预建以下班种模板：

- 全天班：08:00 至次日 08:00。
- A 班。
- N 班。
- P 班。
- NP 班。
- 办公班。

除全天班外，管理员首次启用时填写实际起止时间。管理员还可创建任意自定义班种。

每个班种包含：

- 名称、简称和显示顺序。
- 开始时间、结束时间和是否跨日。
- 显示颜色及文字对比色。
- 是否启用。
- 是否计入值班统计。
- 历史配置版本。

已经用于排班的班种不能直接删除，只能停用。修改时间或颜色不改变已发布历史班次保存的快照，只作用于后续新班次。

## 7. 排班模型

### 7.1 时间规则

- 数据库存储 UTC 时间，页面统一按中国标准时间显示。
- 全天班为当日 08:00 至次日 08:00。
- 跨日班次归属到开始日期。
- 月度、周末和法定节假日统计也按开始日期判断。

### 7.2 排班期间与版本

每个群组、排班角色和月份都有独立排班期间。每个期间可存在多个版本，但同一时刻只有一个当前发布版本。

状态包括：

- 草稿。
- 待发布。
- 已发布。
- 已撤回。
- 已被新版本替代。

重新生成已发布月份时创建新草稿，不直接覆盖当前发布版本。发布新版本后，旧版本保留并写入替代事件。

### 7.3 发布策略

每个群组可配置：

- 自动生成后保存草稿，由管理员确认发布。
- 自动生成后直接生效。

管理员可对单次生成、请假或换班调整覆盖默认策略。成员只看到已发布数据；管理员可以切换查看草稿。

## 8. 自动排班

每个排班角色保存：

- 有序成员列表。
- 默认班种。
- 每天所需人数，医生轮值默认一人。
- 起始日期、起始成员和当前轮值游标。
- 请假重排策略。
- 规则版本。

生成流程：

1. 校验成员、班种、顺序和时间规则。
2. 按固定顺序建立基础排班。
3. 检查停用成员、已批准请假和跨角色时间冲突。
4. 应用请假重排、换班和加扣班等已生效调整。
5. 计算统计和风险提示。
6. 生成差异预览。
7. 保存草稿或按设置发布。

相同输入和规则版本必须生成相同结果。请求带唯一操作编号，重复点击不会重复生成班次。

无法找到可用人员时不强行排班，而是保留“待处理空缺”，通知管理员并阻止无提示发布。时间重叠为硬冲突；连续 24 小时值班显示高风险警告但默认不强制禁止，由管理员处理。

## 9. 手动排班

### 9.1 页面流程

1. 选择排班角色、参与人员及本次可用班种集合。
2. 进入手动排班页面。
3. 选择排班开始日。
4. 输入一轮周期天数，例如 7 天或 30 天。
5. 表格自动生成同等数量的日期列。
6. 表格行为值班人员，列为日期；表头直接显示日期、星期、节假日或调休标记。
7. 表格下方显示所有已选择班种按钮，例如全天班、A、N、P、NP 和办公班。
8. 点击单元格，再点击班种按钮，将班种写入该人员该日期。
9. 提供“清空此格”“清空此行”“清空此列”三个操作。

清空整行或整列必须二次确认，并允许在保存前撤销。快捷操作不能绕过冲突校验。

### 9.2 单次与循环模板

手动填写完成后可以：

- 仅生成从开始日起的一轮。
- 保存为周期模板，并重复应用到管理员指定的结束日期。

保存模板本身不产生正式班次。应用模板时先生成预览，显示时间冲突、请假冲突、连续值班风险、节假日和统计影响，然后保存草稿或发布。

模板保存班种和人员映射的版本信息。成员离开、班种停用或模板规则变化后，再次应用必须重新校验，不允许使用失效引用静默生成排班。

## 10. 请假

成员只选择首尾包含的开始/结束业务日期并按全天提交，不提供半天或时分输入；同时选择请假类型（例如进修、轮科、病假、产假或其他）和选填原因。创建前的受影响班次查询只是可失败、非阻塞提示；完整重排 preview 只在管理员审批阶段生成。

请假时间与班次有任何重叠，该班次即不可安排该成员。

批准前展示：

- 受影响班次和人员。
- 变更前后排班。
- 新增或减少的总值班、周末班和法定节假日班。
- 连续值班和跨角色冲突。
- 无法自动补位的空缺。

群组支持两种策略，并允许审批时单次覆盖：

1. 原轮值不变：仅替换请假期间班次，之后继续原基础顺序。
2. 整体顺延：轮值游标在请假期间跳过该成员，其他人依次提前；请假结束后，该成员在游标再次到达时恢复参与。

自动替班只在相同排班角色中按顺序寻找，跳过请假、停用或时间冲突人员。

## 11. 换班

第一阶段支持两个成员交换各自在中国业务日期今天及以后的已有班次；今天的班次即使已经开始仍可操作，跨日班按开始业务日期归属。

流程：

1. 发起人选择自己的班次、目标成员和对方班次。
2. 系统刷新并预检两个班次、人员资格、请假和时间冲突。
3. 对方手动接受，或按其在该群组的“自动接受换班”设置接受。
4. 若群组要求管理员批准，则进入审批；否则立即生效。
5. 管理员分别设置群组换班/加扣班是否需要审批；成员设置本人是否自动接受换班/加扣班。普通申请下一状态由服务端按两个设置决定。
6. 后端在一次事务中交换两个班次、更新版本、刷新统计并生成事件和通知。

具有 `manageSwaps` 权限的管理员/群主还可走独立直办路径：先生成换班 preview，再直接执行为 `completed`；该路径没有 reason 字段，并绕过对方接受和群组审批开关。普通申请才按成员自动接受和群组审批设置决定下一状态。

换班不会形成加班或扣班次数，因为双方仍各完成一个班次。换班是否改变班次类型和节假日属性，以交换后的实际班次为准。

## 12. 加班与扣班

加扣班表示一名成员代替另一名成员完成某个班次，不是两个班次互换。

示例：A 替 B 完成一个班次：

- A 增加一次加班。
- B 增加一次扣班。
- 该班次的实际值班人员变为 A。
- 原计划人员 B 仍保存在班次历史和事件中。
- 加扣班不改变后续固定轮值顺序。

加扣班由一组不可拆分的关联记录表示，不能只写加班而缺少对应扣班。普通申请 reason 选填，并由目标加班成员接受或使用其自动接受设置；随后按群组审批开关决定是否进入管理员审批，创建前先 preview。具有 `manageDutyAdjustments` 权限的管理员/群主可走独立直办路径，由写接口在事务内校验并直接 `completed`，绕过目标成员接受和群组审批；直办 reason 同样选填，空值省略，当前没有 direct 专用 preview。

每位成员统计：

- 计划班次数。
- 实际值班数。
- 加班次数。
- 扣班次数。
- 加扣班净值，即加班次数减扣班次数。

同一成员先加班一次、以后扣班一次，净值回到零，但两条历史和两个实际班次不会删除。日历显示实际值班人员并标记“加”；被扣班成员的个人事件中显示“扣”。

同一班次同一时刻只能存在一组有效加扣班关系。后续替换必须先撤销当前关系，再创建新的关联事件。

## 13. 并发控制与数据一致性

这是强制验收要求，适用于 Web 和后续小程序。

### 13.1 版本校验

排班期间、具体班次、请假、换班、加扣班和审批记录按当前合同保存并暴露必要版本。客户端只发送对应共享契约声明的预期版本和 operationId，不为统一流程自行补字段；当前新建请假和工作流设置更新没有客户端 operationId。

### 13.2 提交保护

1. 打开换班、请假审批或人工调整窗口时先刷新相关数据。
2. 提交前后端重新读取最新版本。
3. 后端在 MySQL 事务中锁定所有相关班次和申请。
4. 若版本不一致，整个操作不写入任何业务数据。
5. API 返回明确的数据冲突响应和最新摘要。
6. 页面弹窗提示“排班已被其他操作更新，请刷新后重新确认”。
7. 页面自动刷新当前月份和操作窗口，用户必须基于新数据重新提交。

两个用户在同一秒提交同一班次时，数据库串行处理，只有第一项有效操作成功。第二项不得覆盖、重复或产生部分写入。

### 13.3 主动刷新

页面在以下时机检查最新排班版本：

- 浏览器标签重新获得焦点。
- 打开换班、请假、加扣班或人工调整窗口。
- 正式提交前。
- 收到排班变动站内通知后。

系统可以用低频增量轮询提示页面存在新版本，但最终一致性始终由提交时服务器事务保证，不依赖客户端及时刷新。

## 14. 排班事件与审计

### 14.1 排班事件

业务事件只追加、不覆盖，包括：

- 排班生成、手动模板应用、重新生成、发布、撤回和替代。
- 人工修改和纠正。
- 请假申请、批准、拒绝和自动重排。
- 换班申请、接受、拒绝、批准和生效。
- 加扣班申请、确认、批准、撤销和替代。
- 成员、排班角色、轮值顺序和班种变更。

每条事件保存：

- 群组、关联排班期间和业务对象。
- 事件类型和状态。
- 发起人、操作者和审批人。
- 发生时间和原因（若该操作提供）。
- 变更前后结构化数据。
- 受影响人员和班次。
- 统计变化。
- 关联操作编号和父事件。

错误事件不能删除，只能通过新的纠正或撤销事件修正。

### 14.2 安全审计

安全审计与排班事件分开保存，包括登录失败、账号封禁、管理员任免、群组码更新、权限拒绝、数据导出、备份和平台管理操作。

## 15. 日历与页面体验

### 15.1 登录后的默认页面

- 用户登录后默认进入当前月份排班日历。
- 每个日期格直接显示当天值班人员、排班角色和班种。
- 查看值班姓名不需要点击、展开或跳转。
- 单日内容较多时优先完整显示值班姓名，次要时间或说明可以折叠。
- 点击只用于查看详情、原因（若记录提供）、电话和事件时间线。

### 15.2 日历能力

- 当前日高亮。
- “今天”按钮。
- 上一月、下一月和年月选择。
- 电脑月历；手机可切换月历、周历和列表。
- 中国法定节假日名称和调休工作日标记。
- 按排班角色、成员、班种和“只看变动”筛选。
- 班种颜色、文字简称和状态图标同时显示。
- 换班标记“换”、请假替班标记“替”、人工调整标记“调”、加班标记“加”。

### 15.3 快速拨号

值班姓名旁显示电话图标。手机点击后弹出长号和短号供选择，再调用系统拨号；电脑端提供复制号码。若号码未确认或为空，则显示清晰提示，不构造无效拨号链接。

### 15.4 管理工作台

管理员导航包括：

- 当前排班和待处理冲突。
- 自动排班。
- 手动排班。
- 请假、换班和加扣班审批。
- 成员、排班角色和轮值顺序。
- 班种。
- 事件。
- 统计。
- 群组规则和管理员。

已发布班次的人工修改要求填写原因并二次确认。“撤销”创建反向事件，不删除原事件。

### 15.5 视觉与可访问性

- 浅蓝、浅绿和白色为主，保持清新简约。
- 正文字号、行高和字重以医护人员快速阅读为优先。
- 颜色不能成为唯一状态表达，必须同时有文字或图标。
- 管理员选择班种颜色时检查前景与背景对比度。
- 电脑端侧边导航，手机端底部导航和抽屉菜单。

### 15.6 访客排班查看

- 匿名访客通过包含 `visitorKey` 的群二维码进入单一群组只读月历，不公开列出全部群组，也不要求先登录或输入群组码；已登录 guest 可通过受保护 catalog 选择允许加入的群组。
- 初始月历固定为访问当天所在的业务月份；页面只提供上一月和下一月导航，不提供月份输入或选择控件。
- 访客月历返回群组名称、排班角色、班种、值班姓名和已确认的联系电话（用于快速拨号）；未确认号码字段省略。页面通过公开节假日接口显示法定节假日与调休标记，同时高亮当天。
- 访客接口和页面不得返回群组码、换班/加扣班等事件标记与事件记录、统计、审批或管理能力；值班单元不显示“事件”入口。

## 16. 通知

### 16.1 第一阶段渠道

- 站内通知为可靠记录，保存已读和未读状态。
- 浏览器通知为增强能力，权限被拒绝时系统仍可正常使用。
- 通知类型是开放字符串；只有建立明确、已测试的 typed route mapping 时才跳转到对应申请或页面，未知类型和没有安全路由的记录只显示摘要，不拼接通用对象深链。

### 16.2 默认提醒

- 值班前 24 小时和 2 小时提醒。
- 换班、加扣班和请假状态变化后立即提醒。
- 排班发布或修改时只提醒受影响人员。
- 管理员收到待审批、无法补位、冲突和草稿到期提醒。

群组可设置默认提醒时间，成员可在自己的群组设置中覆盖。锁屏通知默认只显示“排班信息有更新”，进入系统后查看姓名和原因（若记录提供）。

PWA 可缓存静态资源和最近查看的排班，但离线时只允许查看，不允许提交任何变更。

## 17. 统计

只统计当前已发布且有效的班次。草稿、已撤回和已作废数据不计入正式统计。

每位成员提供：

- 月度和年度计划班次数。
- 月度和年度实际值班数。
- 按排班角色分类。
- 按班种分类。
- 周末值班数。
- 中国法定节假日值班数。
- 换班次数。
- 加班次数、扣班次数和净值。
- 请假、换班、加扣班和人工调整造成的增减。
- 原值班人员与实际值班人员对照。

周末与法定节假日互斥：若某天同时为周末和法定节假日，只计入法定节假日。调休工作日不计入法定节假日。跨日班按开始日期分类。

班种具有“是否计入值班”属性。办公班默认不计入值班，管理员可以修改后续班次的统计规则；历史班次使用发布时快照。

统计由事件触发增量刷新，并提供按月重新计算功能用于校验。统计缓存可以重建，排班和事件才是事实来源。

## 18. 节假日数据

- 每年根据国务院办公厅正式通知录入。
- 保存日期、节日名称、是否放假、是否调休工作日、年份和数据版本。
- 不在用户访问时依赖第三方节假日 API。
- 新年度官方安排尚未录入时通知平台管理员，未确认日期不错误计为法定节假日。
- 历史节假日版本不被新年度数据覆盖。

## 19. 主要数据实体

核心实体及作用：

- `users`：外部稳定 UID（列名沿用 `cloudbase_uid`）与业务用户状态。
- `user_profiles`：真实姓名等账号级资料。
- `groups`：群组、群组码、群主和规则版本。
- `roster_entries`：管理员预建、等待认领的人员。
- `group_memberships`：用户与群组、权限角色和个人设置。
- `group_member_contacts`：群组内长号、短号和确认状态。
- `schedule_roles`：一线、二线等排班角色。
- `member_schedule_roles`：成员与排班角色的多对多关系及生效区间。
- `shift_types`：班种和版本化配置。
- `rotation_rules`：自动排班参数。
- `rotation_members`：固定顺序和位置。
- `manual_schedule_templates`：手动周期模板。
- `manual_schedule_cells`：模板中的人员、周期日和班种。
- `schedule_periods`：月份、版本和发布状态。
- `shift_assignments`：开始结束时间、计划人员、实际人员和版本号。
- `leave_requests`：请假时间、类型、选填原因和审批状态。
- `swap_requests`：两个班次、双方状态和管理员状态。
- `duty_adjustments`：成对的加班与扣班关系。
- `approvals`：通用审批记录。
- `schedule_events`：不可修改的业务变更历史。
- `notifications`：通知、渠道和已读状态。
- `holiday_calendar`：国家节假日和调休数据。
- `statistics_snapshots`：可重建的月度和年度统计缓存。
- `audit_logs`：安全与平台操作。
- `idempotency_keys`：防止重复提交。

关键约束：

- 活动群组码唯一。
- 群组内待认领真实姓名唯一。
- 同一排班版本中，同一角色、同一时间槽和位置不能重复。
- 同一班次只能有一个当前实际值班人员。
- 同一有效加班必须关联一个有效扣班。
- 所有可变业务对象都有版本号。
- 高频查询按群组、月份、角色、成员和状态建立组合索引。

## 20. 安全、隐私和恢复

- 所有业务访问通过后端接口，不允许前端直接写核心数据库。
- 每个接口校验外部身份、群组成员身份和具体权限。
- 所有输入执行类型、长度、状态和归属校验。
- 排班、审批、换班和加扣班使用数据库事务。
- 登录、群组码管理和敏感接口实施限频；已删除的群组码 claim 不作为可调用入口。
- 匿名访客只通过有效 `visitorKey` 读取对应单一群组；不提供公开群组目录。访客月历只返回 confirmed 电话，省略未确认联系方式、change markers、事件和群组管理数据。
- 真实姓名和电话只在业务必要范围内显示。
- 导出文件默认不包含电话，导出行为写入审计。
- 日志不记录密码、令牌和完整电话。
- 正式数据禁止复制到开发环境。

备份策略：

- 每日自动导出加密备份。
- 保留最近 30 个每日备份。
- 保留最近 12 个每月备份。
- 每季度执行一次恢复演练。
- 群组删除进入 30 天软删除回收期。
- 账号注销后保留排班所需的历史姓名快照，但解除登录身份和联系方式。

## 21. 错误处理

统一处理以下情况：

- 身份过期：引导重新登录，保留未提交表单的非敏感内容。
- 权限不足：不透露其他群组数据，只显示无权限提示。
- 数据冲突：返回最新版本并强制刷新。
- 业务冲突：明确指出请假、时间重叠、停用成员或角色不匹配。
- 无人可排：创建待处理空缺，不悄悄跳过。
- 云函数或数据库失败：事务回滚，不产生部分事件。
- 通知失败：业务操作仍可成功，通知进入重试并显示运维告警。
- 定时任务重复执行：通过任务批次和唯一键保证幂等。

## 23. 部署、域名和备案

### 23.1 环境

- 本地：Win11、Docker、IPv6 域名，可用于开发和内部测试。
- 开发：本地/ECS 开发环境。
- 正式：独立 ECS 环境、正式 MySQL、备案域名和 HTTPS。

### 23.2 正式资源

- Nginx 静态网站托管。
- Nginx 反向代理 `/api` 到 Fastify。
- 本地开发认证（自建认证为后续任务）。
- ECS 容器常驻 Fastify 与 cron/外部调度定时任务。
- ECS MySQL。
- 云存储备份。
- 腾讯云日志、监控和费用告警。

前端与 API 优先使用同一域名，例如 `schedule.example.com` 和 `/api` 路由。正式域名通过 ECS 公网 IP + 备案域名满足 IPv4 网络访问。

### 23.3 备案

正式上线前：

1. 确认现有域名已实名认证且符合中国大陆备案要求。
2. 购买满足备案条件的阿里云资源。
3. 完成 ICP 首次备案或接入备案。
4. 绑定自定义域名、CNAME 和 HTTPS 证书。
5. 上线后按适用要求办理公安联网备案。

公网 IP 直连只用于开发测试，不能作为正式长期入口。

## 24. 自动部署、监控和费用

### 24.1 自动部署

GitHub 保存代码和版本，不作为正式业务服务器。每次提交执行类型检查、单元测试、接口测试和前端构建。合并后部署开发环境，正式环境采用人工确认发布。数据库迁移前先备份，部署失败保留上一可用版本。

### 24.2 监控

- 网站可访问性和证书到期时间。
- API 错误率、响应时间和无权限请求。
- MySQL 容量、连接、慢查询和备份状态。
- 自动排班、提醒、统计任务最后成功时间。
- 未补位空缺和长时间待审批申请。
- ECS 带宽、流量、磁盘与费用。

费用达到月度预算的 70%、85% 和 100% 时通知平台管理员。初期关闭不受控超额计费，确认容量后再决定是否开启。

### 24.3 成本判断

- 本地开发基本不产生云端运行费用。
- ECS 试用机可用于开发期验证。
- 正式环境不存在同时满足中国大陆稳定访问、动态数据库、备案和长期完全免费的可靠方案。
- 小规模正式运行从 ECS 最低配置评估起步。
- 是否升级标准版以实际活跃量、MySQL 冷启动、调用量和压力测试为准，不仅按注册人数决定。

- 微信身份关联现有业务用户（自建认证落地后）。
- 已有 Web 用户首次绑定时验证原账号或一次性绑定码，不能只凭真实姓名接管账号。
- 新用户通过管理员邀请认领成员身份，或通过受保护 catalog 以 guest 身份加入；不恢复群组码 claim。
- 增加微信订阅消息。
- 第一版优先提供日历、电话、请假、换班、加扣班、通知和个人统计；复杂管理仍优先使用电脑网页。

### 26.2 护士排班

护士排班另写独立规格，基于现有群组、成员、班种、事件和通知扩展：

- A、N、P、NP、办公等组合班。
- 每班最低人数和资质结构。
- 连续夜班、休息间隔和禁排规则。
- 技能层级和岗位覆盖。
- 公平性评分和优化排班。
- 锁定部分班次后重新计算其余班次。

## 27. 关键成功标准

医生排班 Web 1.0 达成以下结果才视为完成：

1. 登录后当前月份每天值班人员立即可见。
2. 管理员可以从人员、角色和班种开始生成或手动建立完整排班。
3. 固定顺序、请假重排、换班和加扣班结果正确。
4. 多用户并发修改不能覆盖新数据或产生部分更新。
5. 任一排班变化都可以通过事件追溯前后内容及原因（若该合同/操作提供）。
6. 月度、年度、周末、法定节假日和加扣班统计可核对。
7. 同群组成员可快速拨打当班人员长号或短号。
8. 群组数据和联系方式不会泄露给其他群组。
9. 正式数据有可验证备份和恢复流程。
10. 系统可在中国大陆 IPv4 网络通过备案 HTTPS 域名稳定访问。
