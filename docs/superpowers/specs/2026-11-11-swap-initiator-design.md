# 管理员换班选择实际发起人

用户已确认：发起人指实际提出换班的人，可为换班双方以外的值班人员或管理员；默认当前管理员，真实操作人另行保留。

- 管理员直接换班（Web、小程序）及网页校对产生换班的确认弹层增加“发起人”。沿用现有表单/选择器、蓝白配色和系统字体，不改双方班次选择或换班结果。
- 候选包括当前群组有效值班成员、待认领值班名单、群组管理员及有效平台管理员；不按当月有无班次筛选，不包含访客、停用/已删除人员和其他群组普通成员。
- 新增管理员专用候选读取接口；直接创建输入增加可选 initiatedById，省略沿用当前操作管理员。普通成员创建接口严格拒绝此字段，管理员写入时重新核对候选范围。
- 事件JSON保存发起用户及姓名快照，事件API顶层从快照恢复该用户ID；第三人不写用户外键，避免隐式用户锁。当前操作人归属沿用原外键；无账号旧名单仅保存姓名与名单ID。operatorUserId、审批人、通知操作者、校对操作记录仍为真实管理员。换班双方身份不变，无数据库迁移或依赖变化。
- “有效”按管理员提交时服务端读取的候选快照判断；之后并发停用不改写已读取的历史归属。发起人不是执行权限身份，不为第三人新增用户/资料锁，保留既有业务锁序。
- 待认领名单已有同群组账号身份时，以账号状态为准，不能从旧名单分支恢复停用人员。平台管理员资格沿用应用实际配置集合与数据库标记。
- 网页校对仅换班方案显示此字段。选定发起人用于方案的全部换班步骤；现有计划指纹、并发占用、版本校验与幂等保护保留，并将发起人绑定工作流幂等输入。
- 验证管理员/普通成员权限、未排班人员、平台管理员、无账号名单、无效/跨组人员、默认值、重复请求及两入口请求/事件一致性。浏览器、Node与实体设备证据分别记录。

实施顺序：基线与回归红 → 服务端候选/校验/事件 → 共享客户端及Web → 黄金源/小程序两个入口 → 定向、类型、lint、构建及浏览器验证 → 状态更新、检查点提交推送。生产与体验版交付按各自现行授权边界处理。
