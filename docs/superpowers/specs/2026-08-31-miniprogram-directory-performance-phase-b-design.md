# 通讯录性能诊断阶段 B 设计

## 实测结论

阶段 B 使用 `.72@5fff288` 在小米 14（Android 16、微信 8.0.77、基础库 3.17.1、Wi-Fi）采集的两批共 17 条记录，并用 17 个脱敏 request ID 对照 production API 完成日志。

- 9 次完成搜索的中位总耗时为 1315ms；请求前中位 7ms，接口返回后到可见中位 19ms。
- 完成搜索的首字节中位 1216ms，而同 request ID 的 API 响应中位 250ms；两者差值中位约 992ms。该差值只表示 API 进程之外的等待，不能继续拆分为微信请求调度、上游链路或入口代理。
- 17 次中 8 次被后续输入替代。实测连续输入间隔约 265–450ms，而当前自动搜索防抖为 240ms，因此旧请求已经发出并与新请求并发。
- 转换为 0–1ms、卡片生成 0–2ms，setData 体量约 3KB；没有证据支持大改客户端转换或渲染。
- API 单次响应仍有 14–1790ms 波动，现有完成日志只有总耗时，无法判断鉴权、数据库连接、权限读取、搜索查询或序列化哪一段占主导。

这些数据不支持“只有第一次搜索慢”。已完成的人员首次搜索可为 581ms，另一次首次记录因新输入被替代；慢请求也出现在会话后续搜索。

## 本批行为变化

1. 输入自动搜索防抖从 240ms 调整为 500ms。点击键盘搜索/确认仍立即请求；清空、筛选、分页、缓存、排序和错误处理语义不变。500ms 来自本次 265–450ms 的连续输入间隔，用于避免用户仍在输入时发出旧关键词请求。
2. 仅当测试工具正在记录时，小程序请求增加 `X-Schedule-Directory-Diagnostics: v1`。普通请求和正式 API 响应体不变。
3. API 只对带上述诊断头、且 `X-Schedule-Client-Platform: miniprogram` 的通讯录列表请求返回标准 `Server-Timing` 响应头。记录鉴权、数据库事务连接等待、权限、发布批次、工号别名、主查询、联系方式、计数、查询合计、结果转换、序列化和服务端总耗时。
4. 现阶段无法可靠测量入口排队，明确返回“不支持”；目录列表没有应用层结果缓存，明确返回“none”。实例是否处于启动后 60 秒内及实例存活时长只作为冷启动上下文，不伪装成实例启动耗时。
5. 客户端只解析固定白名单字段并写入最多 20 条内存诊断；不保存原始 Header，也不记录查询词、筛选、账号、群组、权限、游标或响应体。

## 暂不修改

- 不修改 API JSON contract、数据库 schema 或索引。
- 不改权限锁、搜索排名、别名/拼音/号码查询结构、连接池和部署拓扑。
- 不下载或缓存完整人员通讯录，不增加无上限历史缓存，不发送预热搜索。
- 等 `.73` 的 Server-Timing 真机数据指出单一服务端阶段后，再决定是否需要独立的数据库或查询优化批次。

## 验收口径

- 回归测试证明 265ms 与 450ms 的连续输入不会发出中间请求，静止满 500ms 后只发送最新关键词；显式确认不等待 500ms。
- 无诊断头、非小程序平台、facets 和 lookup 不返回 Server-Timing。
- 诊断头只包含固定阶段名、毫秒数字和固定状态，不包含业务内容。
- 小米 14 下一轮按首次、重复、不同词、带筛选、科室及可行时 Wi-Fi/移动网络执行；每个主要场景尽量 5 次。修改前后对比只使用真实数据，无法取得的项目标为“待小米 14 体验版实测”。
