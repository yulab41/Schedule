# Skyline 排班矩阵踩坑与后续守则

本页只保存可复用结论；实现细节与回退点见 [ADR-0005](../decisions/ADR-0005-worklet-matrix-engine.md)，验收用例见[测试计划](../testing/test-plan.md)。

## 已验证结论

- 目标 Android 上，PC 模拟器通过不代表 Skyline 真机通过；实体 Android 是滚动与手势的唯一放行门槛。
- 冻结首行/首列必须只有一套坐标源。当前方案是单一 WXS 触摸入口维护 X/Y，日期层读 X、人员层读 Y、班次层读 X/Y、进度条读 X；同一帧直接 `setStyle(transform)`。
- 高频路径不得经过 `bindscroll → JS → setData`，不得让多个 `scroll-view`、Worklet、WXS 或兜底逻辑同时追赶坐标。
- WXS 的 Skyline 能力必须先做最小真机探针。不得假设浏览器 RAF 时间戳、完整 JavaScript 语法或长期有效的节点句柄。
- 渲染提交后要恢复坐标；快速惯性必须使用有限数值、固定 16ms 步长和边界钳制，避免 NaN 导致主体冻结而单轴层仍移动。
- 20×30 共 600 格时，矩阵热路径使用浅层内置 `view`，不要实例化 600 个自定义组件。视觉样式仍与保留的独立组件做契约对照。

## 这次踩过的坑

1. Web 的“同一 DOM 网格”不能原样搬到小程序；拆成多个原生滚动容器后出现表头追赶、延迟和黏滞。
2. Skyline 官方优先路径 Worklet 在目标 Android 上没有执行，PC 却正常；直到蓝点/黄点最小探针才确认 WXS 可用、Worklet 不可用。
3. 嵌套横纵手势、simultaneous/exclusive 协商和原生滚动代理在真机上出现轴被吞、只能滑一次或只有单层移动。
4. 第一版 WXS 长期缓存节点、静止后 `setData` 重建渲染树，导致第二次手势失效或松手回零。
5. 惯性误用浏览器 RAF 时间戳，真机回调无该参数后产生 NaN，快速滑动回弹并锁死。
6. 600 个格子自定义组件加首次 `SelectorQuery → setData` 造成进入页面 3–5 秒无响应；改为浅层格和同步窗宽边界后，只剩进入约 500ms 内抢操作时的短暂卡顿，随后滚动和点格均流畅。

## 为什么一开始没有采用当前方案

- 官方 Skyline 文档首先提供 Worklet、手势组件和 `scroll-view`，WXS 响应事件文档主要以 WebView 为背景，无法预先确认目标 Android 的 Skyline 支持情况。
- 在实体机探针前，直接押注 WXS 会把平台兼容风险带入完整矩阵；PC 模拟器又错误地放大了 Worklet/原生滚动方案的可信度。
- 当前方案不是常规表格组件，而是针对 20×30 有界规模的四层电子表格渲染器，需要先证明输入能力、坐标恢复、惯性和点击语义。

## 后续开发硬规则

1. 新原生能力先做一个页面、一个节点、一个事件的真机探针，再确定架构。
2. 每次矩阵改动必测：首次 500ms、连续快/慢滑、松手惯性、快速反向、先横后纵、先纵后横、点格、撤销、退后台再回来。
3. 坐标只允许一个所有者；滚动帧内禁止 `setData`、网络、同步 API、SelectorQuery 和整矩阵替换。
4. 任何渲染提交都要验证第二次与跨轴手势；任何惯性都要验证无时间戳 RAF 和全程有限数值。
5. 模拟器只用于结构诊断；用户实体 Android 明确通过后才能冻结方案或进入下一阶段。
6. 不为目前仅约 500ms 的首入抢操作短卡立即引入虚拟化。正式业务页优先在跳转前预取数据并显示就绪态；只有真机指标不达标时，才单独评估成员行虚拟化。

## 当前优化边界

P1 继续保留现有四层 WXS 引擎。2026-08-22 用户确认 P1 通过：正常进入后横纵滚动、冻结层、进度条、点格和撤销均流畅，接受“进入后约 500ms 内立即操作可能短卡”为 PoC 边界。正式业务页仍先做预取与就绪态，不直接为该边界引入虚拟化。
